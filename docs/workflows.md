# Reusable workflows

Every workflow here, what it does and what it takes; the scripts behind them; and the organisation's secrets and variables.

## Reusable workflows

Call them at `@v7`, every one of them, the release included: never at a pinned commit (`v7` is a protected ref that only an administrator moves, #136); a breaking change ships as the next major (`v8`), and the previous one stays where it is. A stack suffix
(`-wp`) appears only when the steps are specific to that stack. A workflow
with a `central-ref` input reads the scripts, profiles and policy at that
ref; empty, the default, at the very commit its `uses:` line resolved to
(`job.workflow_sha`, #287), so a caller that pins a SHA runs that commit's
scripts with nothing else to set. A workflow another one calls is named at
`@v7` inside it, and runs its own commit's scripts. A caller that still passes `central-ref: v7` keeps reading the moving tag.

When an accepted issue closes as completed: *Done* (closed as not planned: left where it is). Any other lane is left alone (a person accepts it, or the workflow that opens its issues labels them). The gate still asks the policy itself. Called from `issues.yml` (on `opened`, `edited`, `labeled` and `closed`). In DiluxOne/.github, a person's acceptance of a decision whose PRD names `Repositories` opens a sub-issue in each repository it selects ([`scripts/decision.py`](../scripts/decision.py) `open`, #189). | `label`, `workflow`, `central-ref`; secret `DILUX_BOT_PRIVATE_KEY` (with the organisation variable `DILUX_BOT_CLIENT_ID`), optional: without it, the Project and the assignee are left alone and the G1 result stays in the job's log |
| [`security-fix.yml`](../.github/workflows/security-fix.yml) | Reusable, called only from a private repository (DiluxOne's is `DiluxOne/security`, every hour, by hand from its default branch, and on a person's comment there, which runs only the fixes a maintainer answered; it refuses to run from a public one, whose logs and artifacts anyone could read): a security advisory's fix, written where only the organisation sees it (#194). First, each issue there labelled `security:intake` (a vulnerability the triage moved there from a public issue, #287) gets its draft advisory in the repository it came from, opened with dilux-security's key, its author credited and invited to it, and closes with its link (`scripts/advisory.py intake`). Such an advisory, and one the nightly review opens, is not confirmed until the triage confirms it: an open `security:unvetted` issue of the bot's there says so (never the advisory's text, which those it is shared with can edit); it is triaged and capped like a report, and `security-patch.yml` builds no patch while that issue is open (a maintainer may close it). Each advisory in triage or draft is claimed with an issue in the private repository, "Fix <GHSA> in <repository>" (one attempt per advisory, unless a maintainer sends a failed one back: they answer on the claim's issue what to change, the comment starts a run, and it tries again with that answer as guidance, one attempt at a time, #313). An agent (Bash and the network, on a stranger's text, with no key or token of the App) clones the public repository, writes a failing test and the fix, and its `make pre-pr` runs in the same job; a patch is all that leaves it. A clean job puts the patch and the notes on a branch `fix/<ghsa>` there, in commits GitHub signs, and writes the fix, the checks and the patch into the issue. One in triage is triaged there on its own (#247): when the agent's verdict is a vulnerability it reproduced with a failing test and fixed with checks that did not fail (`scripts/advisory.py advance`), the bot moves the advisory to draft with a token for that one repository; otherwise it stays in triage, and the issue says why, for a maintainer. At most two in triage are taken a run (`TRIAGE_PER_RUN`), since a stranger's report starts a paid run with no person in between; a draft stays private and is reviewed before anything is published. The advisory's temporary private fork is not used: GitHub lets only people and teams into it. It never merges nor publishes: `security-patch.yml` publishes a fix whose checks passed once its advisory is a draft and a maintainer approves it (#247, #287). The advisories are read and moved with dilux-security's key (`DILUX_SECURITY_PRIVATE_KEY`, `DILUX_SECURITY_CLIENT_ID`, only in the private repository), so dilux-bot needs no advisory permission; the caller ([`workflow-templates/security-fix.yml`](../workflow-templates/security-fix.yml)) passes `DILUX_BOT_PRIVATE_KEY`, `DILUX_SECURITY_PRIVATE_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`. `DX_AUTOPILOT=off` stops it. | `central-ref` |
| [`security-patch.yml`](../.github/workflows/security-patch.yml) | Reusable, called only from the private repository that holds the security fixes (`DiluxOne/security`, every hour and by hand; it refuses to run from a public one): a recorded fix, once its checks passed and its advisory is a draft, becomes a patch on the version in production once a maintainer approves it (#247, #287). [`scripts/carry-lock.py`](../scripts/carry-lock.py) `fix`; one that does not apply is left to a person, on the issue), and the claim closes (`patch:released`); the lane accepts that issue because the advisory is published with the version patched, and its pull request merges on its own only while its commits are exactly the released fix (`autonomy.py lane-merge`). The caller ([`workflow-templates/security-patch.yml`](../workflow-templates/security-patch.yml)) passes `DILUX_BOT_PRIVATE_KEY`, `DILUX_SECURITY_PRIVATE_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`. `DX_AUTOPILOT=off` stops it. | `central-ref` |
