# Reusable workflows

Every workflow here, what it does and what it takes; the scripts behind them; and the organisation's secrets and variables.

## Reusable workflows

Call them at `@v5`, every one of them, the release included: never at a pinned commit (`v5` is a protected ref that only an administrator moves, #136); a breaking change ships as the next major (`v6`), and the previous one stays where it is. A stack suffix
(`-wp`) appears only when the steps are specific to that stack. A workflow
with a `central-ref` input reads the scripts, profiles and policy at that
ref (default `v5`), not at the ref of its `uses:` line: a caller that pins
`uses:` to a version passes the same version as `central-ref`.

| [`autopilot.yml`](../.github/workflows/autopilot.yml) | The autopilot (#83). `mode: start`, from `issue-triage.yml` when a person accepts an issue: if the autopilot is on and the issue is ready (G1), Claude writes the Spec into the issue (G3, sealed); the workflow opens a draft pull request, labelled `autopilot`, whose body is the Spec as a checklist; Claude then works the criteria in order, one commit each (its subject ends with `(C<n>)`), pushed, its box ticked only once GitHub has the commit (`scripts/autopilot.py tick`, which checks that the commit is there, not what it does: that is the review's and the criteria's tests' to judge), and, once every box is ticked and it has run the repository's checks, marks the pull request ready for review (`finish ready`, which refuses while a box is open), or says where it stopped and why (`finish stop`, `needs-human`). `mode: continue`, from `issue-triage.yml` when `autopilot:continue` is added to the issue (by a person, or by the workflow when a run ran out of turns or time with criteria left): resumes from the branch and the unticked boxes (or, with every box ticked and the pull request still a draft, only runs the checks and the finish), up to `autopilot-runs` (5) runs per issue; a person who took a pull request back removes `needs-human` first. The agent runs every command in the foreground: nothing tells it a background task finished, and the run ends when it stops. A run never ends in silence: otherwise the workflow comments, adds `needs-human` and fails (`autopilot.py end`); and when that step itself fails before it says its verdict, "The last resort" leaves the comment and the label anyway. dilux-bot's token lives 60 minutes, so the run mints one per phase (the Spec and the draft; the work, whose step is capped at 55 minutes; the end, always), and no step writes with a token older than its life. Every run writes its account (read, ran, changed, how it ended) to the job summary and keeps the agent's transcript, tokens and keys redacted, as an artifact; a work step killed by its timeout leaves no execution log, so both come from the session the CLI kept as it went (`autopilot.py work-log`), with a result that says it was stopped; the issue's board links the pull request, the run and the criteria done. `mode: fix`, from `org-pull-request.yml` when such a pull request's review blocks: one round of fixes; after `autopilot-rounds` (3) it labels it `needs-human` and stays out of it. One run per issue; where the repository's jobs run. Its merge is `auto-merge.yml`'s decision by policy ([`scripts/autopilot.py`](../scripts/autopilot.py) `decide`). | `mode`, `issue`, `pr`, `central-ref`; secrets `CLAUDE_CODE_OAUTH_TOKEN` (or `ANTHROPIC_API_KEY`), `DILUX_BOT_PRIVATE_KEY` |

| Variable (organisation, private repositories only) | `DX_RUNNER` | `self-hosted`: the shared workflows' jobs run on the organisation's runners (runner group `private-repos-vm`, label `diluxone`, on `vm-gh-runner-01`) instead of `ubuntu-latest`, so the private repositories spend none of the plan's minutes. The release, the credentials check and the reproduction stay on GitHub's runners: they handle secrets, or code written from an issue's text, and the VM is shared with AI Studio. What does run there holds the Anthropic and dilux-bot keys; that is safe only because the private repositories take pull requests from the maintainer, the maintainer's agents and Dependabot alone, and AI Studio is the maintainer's too (`runner-vm.yml`'s header). Public repositories do not see it and stay on GitHub's runners. Every job runs in a fresh container of `ghcr.io/diluxone/runner` that takes that one job and is discarded (`scripts/runner-vm/dx-runner-slot.sh`, one systemd slot per runner, registered just in time through the `dilux-runner` App, whose only permission is the organisation's self-hosted runners; its key lives on the VM alone), and the slot removes what the job left before the next one (its containers, its checkout, and the volumes and networks of its wp-env, which docker compose keeps past the containers), so no job sees what another installed, nor its databases. Each slot has its own `WP_ENV_PORT` and `WP_ENV_TESTS_PORT` (9000 + 20 × slot, and the next) and its own folders under `/data/runners-dx/d<n>`, so wp-env suites side by side never share a port. The VM brings itself to this state on every boot: `dx-provision.service` fetches `scripts/runner-vm/provision.sh` from `main` and runs it, so a merged change reaches it on its next start (on a new VM the only manual steps are the App's key and IDs in `/etc/dx-runner/app.pem` and `app.env`, and `provision.sh --install`). Every job gets the VM's Docker socket, which wp-env needs and which is root on the VM, so a job could read that key; it can only register runners, and only the private repositories, with pull requests from the maintainer, the maintainer's agents and Dependabot alone, run there; `plugin-tests-wp.yml` derives from those ports the addresses every E2E suite reads, `WP_BASE_URL` (the development site) and `WP_NETWORK_URL` (the tests site), so a repository's Playwright configs read those two and default to its own ports. The image carries Chromium's system libraries, so a job there installs the browser without apt (`--with-deps` only on GitHub's runners). Set it to `github` to send every job back to GitHub's runners. |
