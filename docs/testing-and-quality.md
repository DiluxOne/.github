# Testing and quality

How a change proves what it does, in every DiluxOne repository. The rule is [test first](../rules/test-first.md): a change that alters behaviour starts with the test that shows it. It is enforced by the "Test first" check, and the review checks it too: the check proves the test fails before the change and passes after it; the review reads whether the test is the right one (it tests the cause, not the symptom, and what must not change).

## The "Test first" check

[`test-first.yml`](../.github/workflows/test-first.yml) runs on every pull request of every repository (from [`org-pull-request.yml`](../.github/workflows/org-pull-request.yml), the required workflow, and from this repository's own `pull-request.yml`). [`scripts/test-first.py`](../scripts/test-first.py) decides:

| The pull request | The check |
| --- | --- |
| `docs`, `style`, `ci`, `chore`, or any type but `fix` and `feat` | Passes, running nothing: "a `<type>` pull request alters no behaviour the check tests: no test is run". |
| `fix` or `feat` (with a `!` too) in a repository that declares no `test-first:` | Fails, saying how to declare it; the daily drift check lists the repository. |
| `fix` or `feat` that adds or changes no test | Fails: "A test that fails before the change is missing", with where its tests go. A release scenario, a fixture or an expected output is never a test. |
| A test that does not pass at the head | Fails, naming it. |
| `fix` whose tests all pass at the base, or only break there (an import error) | Fails: "The test does not show the bug", naming it. A fix's test fails on an assertion at the base. |
| `feat` whose tests all pass at the base, or only break there (an import error, a missing file) | Fails as a missing test: the test tests nothing the feature adds. A feature's test asserts on what it runs (a script's exit code and output, a function's result), so it fails an assertion at the base, the same as a fix's (#845). |
| A test that could not run (its setup failed, or it took longer than its way's `minutes`) | Fails as "could not run": no verdict never passes. |
| Otherwise | Passes: "Test first: `<test>` fails at the base and passes at the head". |

The check a ruleset requires is the `verdict` job, "Test first" (#842): it reports on every pull request, green when the tests passed or there was nothing to run, red when the plan ("Test first (plan)") or the tests failed, were cancelled, or did not run while the plan said they would.

Each test it finds runs twice, at the base's tree with the head's test file in its own place, and at the head, through the reproduction's sandboxes ([`scripts/repro-sandbox.sh`](../scripts/repro-sandbox.sh) and [`scripts/repro-run.sh`](../scripts/repro-run.sh) `run-ref`, with `TEST_REF`): on GitHub's fresh runner, with no secret, no network for the test and a read-only token, so a fork's tests run as safely as a report's reproduction. The verdict, and each test's outcome at the base and at the head, go to the job summary. A pull request with more than 20 tests is asked to split.

## How a repository declares its tests

Where tests are and how they run is data: `test-first:` in its kind's pack (`kinds/<kind>/pack.yml`), then in `repos.yml` under its name, then in its own `.github/review-policy.yml`, each adding to the one before, read from the pull request's base so it cannot exempt itself.

```yaml
test-first:
  setup: [composer install --no-interaction --prefer-dist --no-progress]   # its dev tools, with the network, on the base's checkout, before any test is in place
  tests:
    - paths: ["tests/Unit/**/*Test.php"]   # a file under these is a test
      way: unit                            # run by this way of its `repro:`
      check: "tests / Unit"                # optional (#842): the required check that runs them, which gate G7 waits on
  not-tests: ["tests/**/fixtures/**"]      # never a test, whatever `tests` says
```

Each `way` is a reproduction way of the same declaration's `repro:` ([`scripts/repro-ways.py`](../scripts/repro-ways.py)), so a kind says how it runs a test in one place, and the check reuses its sandbox, command, report and time limit. Every pack declares one; so does this repository. `check:` (#842) names the required check that runs an entry's tests: gate G7 counts an autopilot pull request's criterion met only once that check concluded success at the head; an entry with none is "test-first / Test first"'s, for a `fix` or `feat` pull request only.

## In this repository

A fix or a feature here comes with a pytest test under `tests/repro/` or `tests/workflows/`, run by the `python` way of `.github/review-policy.yml`, and by "Scripts (self-tests)" (its `check:`). The ruleset "own checks" requires that check and "test-first / Test first" on main (repos.yml `required-checks`, written by `sync-repos.py own-checks`, #842): a pull request whose tests are red cannot merge. A script's own `--test` case cannot run at the base apart from the script's code, so a self-test case alone fails the check; keep adding them, beside the pytest. A test never cuts a workflow's text between two literals (`text[text.index("..."):text.index("...")]`, `text.split("...")[1]`): it breaks on a rewording and passes when the step breaks. It finds the step through YAML and runs its `run:` with stubs on PATH (`tests/workflows/steps.py`), or calls the script under `scripts/` that holds the logic; `scripts/literal-slices.py` fails the scripts job on a new one, naming the test, and its list of the files that did before (#845), each with its number of slices, only shrinks: a new slice in a listed file fails as well. The release scenarios (`tests/release/`), fixtures, the reproduction's examples (`tests/examples/`) and the AI's evaluation sets (`evals/`, below) are never a test.

The scripts job of `pull-request.yml` runs every script's `--test` and the whole of `tests/` with pytest; `make pre-pr` runs what the pull request and the merge queue run.

A release scenario's cleanup (`cleanup` and `clear` in `scripts/release-scenarios.py`) never closes a pull request while it sits in the test repository's merge queue, where closing it would knock the other scenarios' pull requests of its merge group out unmerged: it waits for it to leave (at most `QUEUE_LEAVE`, 120 seconds), closes nothing once it merged, and closes it otherwise (#936).

## How the AI is measured

Every AI step of the flow has its evaluation set (#735), so a change to a step's AI is scored, once a week and by hand (#941), not found out from the flow's failures. A set is data under `evals/<step>/`: `cases.json`, real cases from the organisation's public repositories (a private one's code would show in this public repository's logs), each with its `expect`ed outcome, and `baseline.json`, the score of the last whole run. One runner, [`scripts/evals.py`](../scripts/evals.py), replays each case with the step as the checked-out branch has it (its own prompt and its workflow's arguments: what is measured is what ships) and grades it deterministically wherever a grade exists; a model judges only where none does, with its rubric in the case.

[`evals.yml`](../.github/workflows/evals.yml) runs once a week for every step with a set, and by hand for one step, for every step but the review (never on a pull request, #941: replaying whole autopilot rounds on every push spent most of the engine's model use; the autopilot's replay now runs one fix round, `EVAL_ROUNDS`, not `autopilot-rounds`): the review's set is run by its own workflow, [`review-eval.yml`](../.github/workflows/review-eval.yml), through [`scripts/review-eval.py`](../scripts/review-eval.py) (each case played 3 times and scored on its median, the set checked before any paid review, #847), once a week and by hand too (#941), whose paths are the review's row below, and `evals.py` runs review-eval.py's commands for it (`collect`, `run`, `score`, `baseline`), never a copy of its grade or gate. `evals.py steps` maps changed files to steps (the paths below say which files count for which step, to choose what to run by hand); the weekly run plays every step with a set but the review, and a run by hand the step it names, each as the check "AI evaluation (<step>)". Each case is replayed in a job of its own (`evals.py matrix`, `evals.py run <step> <case>`), with its step's time for one case, and a job per step merges their results (`evals.py merge`) and scores them. A step's set fails the check when its score is worse than its baseline by more than one case (a model does not answer the same twice), compared by rate (passed / cases, against (baseline passed - 1) / baseline cases), so a change that adds or removes cases is compared fairly, or by any case when the baseline passed one case or none (the autopilot's 1 of 6 fails at 0 of 6); the review's gate is review-eval.py's exactly: a slack of one case on each count, and an absolute floor on the found side whatever its baseline (#930): it fails when it finds fewer than `review-eval.found-floor` of policy/review-policy.default.yml (0.3, a share of the flag cases, rounded up, never fewer than one case), so a review that finds none always fails, and `review-eval.py baseline` writes no baseline below it. Its score table gives each flag case its reason, play by play: found, a finding in the file outside the fixed lines (and how far), one rejected by verification, no finding in the file, or not reviewed (a play whose answer does not account for every changed file the brief showed, its `examined` list, is a review that did not finish, as production blocks it: "did not examine every changed file", never clean, #953); the summary ends with the run's results as a baseline, between `--- baseline review ---` and `--- end ---`, for the pull request to commit. A case left not replayed (its job ran out of time, or failed) fails the check too, by its name, as the runner's failure and not the step's score (the review keeps review-eval.py's slack of one case not reviewed). Paid: each case is one model run (an autopilot case, a whole work round), so it runs only from a branch of this repository, never a fork's.

What counts for each step (what to run by hand after a change), beside `policy/autonomy.yml` (the model and AI settings, which count for all six), the runner and its workflow (`scripts/evals.py`, `.github/workflows/evals.yml`, which count for the five steps `evals.yml` runs) and its own set, `evals/<step>/**`:

| Step | Its paths | The grade | Where its cases come from |
| --- | --- | --- | --- |
| `triage` | `.github/workflows/issue-triage.yml`, `scripts/triage-brief.sh` | The verdict's `category`, `duplicate_of` and `exists_in_pro` equal the case's record. | _Its own issue: the cases come from GitHub (dilux-bot's triage records)._ |
| `repro` | `.github/workflows/issue-repro.yml`, `scripts/repro-ways.py` | The test the step writes fails at the case's base on an assertion (`reproduced`), run as the "Test first" check runs it. | _Its own issue, with its replay:_ `collect` already gives the reproduced bugs (`the bug reproduced from #N`, with `tests/repro/test_issue_N.py`), at the commit before the fix. |
| `spec` | `.github/workflows/autopilot.yml`, `scripts/autopilot.py` | The PRD and the Spec pass the issue schema (G3), and `### Spec: files` names at least half of the files the merged pull request changed (tests and the changelog aside). | `collect`: the accepted issues whose merged pull request changed tests (at most 20 files, never a revert), at its parent. |
| `autopilot` | `.github/workflows/autopilot.yml`, `scripts/autopilot.py` | The merged pull request's tests pass on the tree the production's loop leaves: the work, then the review and its fix rounds (below), through the same sandboxes. | `collect`: the same issues; the case's tests are the merged pull request's that are valid alone. |
| `review` | `review-profiles/**`, `kinds/*/review-profile.md`, `kinds/*/rules.yml`, `policy/review-policy.default.yml`, `scripts/review-brief.sh`, `scripts/local-review.sh`, `scripts/review-verify.py`, `scripts/review-examined.py`, `scripts/review-count.py`, `scripts/review-eval.py`, `scripts/policy.py`, `.github/workflows/claude-review.yml` | `flag`: a known bug is found again inside the lines its fix changed; `clean`: the pull request is not blocked; each case reviewed as production reviews a pull request (claude-review.yml's review and verify steps, on the brief for its pull request in full mode, #930), played 3 times, scored on its median (#234, #847, review-eval.py's). | `collect` (`review-eval.py collect`): the review's threads on the public repositories' merged pull requests (GitHub, `GH_TOKEN`), at least 10 of each kind. |
| `reply` | `.github/workflows/review-reply.yml` | A model judges, with the case's `rubric` (the only judged step: the outcome is words): the thread is resolved, and no further change is asked. | _Its own issue: the cases come from GitHub (review threads a mention answered, then resolved)._ |

The steps with no set yet (`triage`, `repro`, `reply`) are in the runner's table, with their paths and grades; `evals.py steps` lists only a step with a set, so a change to them runs nothing until their set lands.

**Adding a case.** Run `evals.py collect <step> [N]` (N cases, 6 by default; the review's, N of each kind, 10 by default), read what it wrote to `evals/<step>/cases.json`, keep the real cases that say what the step must do, and commit them in a pull request a person merges, like any change to `evals/` (high risk). A case written by hand has the same shape: `id`, `repo`, the refs (`base`, and `merge` or `head`), the step's own fields (`issue`, `test`, `type` and `files`, `tests`, `pr`, `thread`), and `expect`. A spec or autopilot case pins its issue's `title` and `body` (`collect` reads them once, with `GH_TOKEN`; by hand, the issue's text as it was when its fix merged): the replay reads them from the case, never from GitHub, so an edit to an old issue cannot change a case or its score, and a case without them is not replayed, by name.

**A valid case** (#840). A case of `evals/spec/` or `evals/autopilot/` is valid only if it passes on its merged fix, fails on an assertion at its base, and does not assert the fix's own literals; a case that is not measures something else than whether the step solved the task, so it can neither gate nor guide a change. `evals.py validate [STEP...]` checks each case from its repository at its `base` and its `merge`, with no model: an autopilot case's `tests`, as merged, run through `test-first.py`'s sandbox, pass at the merge and fail at the base on an assertion (`reproduced`; a test that breaks there without one, an import or collection error, is no measure, and at least one must fail); a spec case's grade passes on its merged issue's own Spec and fails on its PRD alone; and no literal of 30 characters or more that the case asserts (a string inside a Python test's `assert` statements, any quoted string of another test) is in the merged fix's added lines (`git diff base merge`, every file under `tests/` left out), nor is a string literal of those lines in a spec case's `files`. Each case that is not valid is printed by its id with the check it fails (`merge`, `base`, `literal`, or `facts` when its repository could not be had), and the command exits 1. `evals.yml` runs it in the job "The cases are valid" before any case is replayed, so a set with an invalid case is not paid for, and the score job waits on it: a set that failed it gets no score, no results and no baseline (the job fails saying so). `collect` keeps only valid cases, the set's own first (as pinned), then the history's, never one twice: an autopilot case keeps the merged tests that are valid alone, and a case with none, or a spec case that is not valid, is left out. Its tests run in the runner's sandbox, so a new set is collected in Actions: `evals.yml` by hand with `mode: collect` and a `step` runs `evals.py collect <step> 6` with the job's read-only token (fewer than six valid cases fails the job), validates and replays that set, and keeps it, never scored against the old baseline, as the artifact `evals-<step>-collect`: `new-cases.json` (the cases not already in the set), the whole `cases.json`, and the run's `results.json` for `evals.py baseline <step> FILE`. It pushes nothing: a person commits them in a pull request.

**The autopilot's replay is the production's loop** (#840). A case runs what the autopilot runs on an accepted issue: the draft (its branch, title and body, `autopilot.py`'s), the work round (`prompt_work`, with the arguments `autopilot.yml` gives it), then the review the pull request would get (`scripts/local-review.sh`, the change's own, with the same brief, profiles and policy, on the draft's title and body), and while it blocks, a fix round (`prompt_fix`, the review's findings in `.dx-io/review.md`, the work step's arguments in mode `fix`), up to the production's limit, `autopilot-rounds` of `policy/autonomy.yml`, never a constant of its own. The merged tests are graded on the tree the last round leaves. A review that gives no verdict leaves the case not replayed. Its job's time covers the work and every round, within a hosted job's 360 minutes.

**The baseline.** A new set's `baseline.json` is `{"pending": ...}` until its first whole run. A step that has never had a baseline (not in `BASELINED` in `evals.py`) whose baseline is missing or pending is not gated: its check passes with a warning, and its summary and log carry the whole run's results, in the format `evals.py baseline` reads, between the lines `--- baseline <step> ---` and `--- end ---`. Saved as FILE, `evals.py baseline <step> FILE` writes the baseline (only from a whole run, every case replayed; for spec and autopilot, from a run of every case of the set, with every case valid by `evals.py validate`, which it runs: it refuses otherwise, naming the cases), in a commit a person reviews, and the step joins `BASELINED`; the workflow never pushes it. A baseline that cannot be read, is not JSON or is neither a score nor pending fails the check, and so does a missing or pending one for a step in `BASELINED` (spec and autopilot; the review's is review-eval.py's, which fails closed too): the check could not tell, and it never passes quietly. A change that should move a score does the same from its run's results (the artifact `evals-<step>`). `evals.py run <step>` and `evals.py score <step> FILE` do by hand what the workflow does; `evals.py --test` checks every grade, the mapping and the review's gate offline, in the scripts job. For the review, `evals.py collect|run|score|baseline review ...` runs `review-eval.py` with the same arguments (`run review --play N`, `score review FILE...`, one file per play).
