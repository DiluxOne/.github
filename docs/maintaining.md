# Maintaining this repository

For whoever changes `DiluxOne/.github`: what the tokens may do, and how a change ships to every repository.

**What waits on a maintainer**, in every repository at once: the pinned issue "What waits" ([`run:waiting`](https://github.com/DiluxOne/.github/issues?q=is%3Aopen+label%3Arun%3Awaiting), rewritten every day by `waiting-digest.yml`), and [the open issues and pull requests labelled `needs-human`](https://github.com/issues?q=is%3Aopen+org%3ADiluxOne+label%3Aneeds-human) (a failed build of the runner image, a week's digest with a proposal, a pull request the autopilot handed over). Every automatic decision says on its issue's board which rule it followed, with the link (#188).

Every place the bot's token is minted asks only for what that job does: the review, the replies and the triage get `contents: read` while the model runs; `contents: write` is minted only by the merge, the reproduction push, the weekly learnings, and the step that resolves review threads after the model has finished (resolving a thread is a write on the repository), which nothing that read the pull request's text ever holds. Tags are not creatable by `dilux-bot` at all: the ruleset an adopting repository sets at step 3 allows `X.Y.Z` tag creation to administrators and the release App only, and this repository's `v*` tags (the moving `v7`, the frozen `v5`, `v4`, `v3`, `v2` and `v1`) can be created, moved or deleted only by administrators (ruleset `moving tags`: creation, update, deletion). The wordpress.org credentials live in the repository environment `wordpress-org`, whose deployment policy admits only `X.Y.Z` tags and `main`, so no pull request or branch job can read them; the check `svn-auth-check.yml` runs inside that environment.

Almost everything here is high risk, and a human merges it. A change that touches only the pages people read (`README.md`, the Markdown of `profile/`, and `docs/` except what agents and the review read as rules: `docs/agents.md`, `docs/architecture.md`, `docs/testing-and-quality.md`, `docs/model.md`) can merge on its own under the usual conditions; [`.github/review-policy.yml`](../.github/review-policy.yml) lists the rest, and `policy.py --test` fails when a file is in no list. After merging, tag
the exact version (its GitHub Release follows, from `engine-release.yml`; the
release pull request rebuilt `CHANGELOG.md` with `scripts/changelog.py build
--next`; [versioning.md](versioning.md) says what a major is for a caller) and
move `v7` (or cut `v8` for a breaking change: `scripts/next-version.py
--tag-prefix v` says which). Moving `v7` also ships the review
profiles, the packs, the default policy and the organisation's required
workflow, which every repository on `v7` reads from that tag. A run that
already exists keeps the workflow it was created with: re-running a failed
job after `v7` moved re-runs the old workflow. Reopen the pull request, or
push to it, for a run on the new one. `v5`, `v4`, `v3`, `v2` and `v1` stay
where they are.

A change to a template in [`workflow-templates/`](../workflow-templates/) reaches no repository by itself: each one has its own copy, its caller. The daily drift check lists every caller that differs from its template, with the job and the template's path (it compares what the jobs do, never their comments, so a template's comment can change without putting any repository out of step), in the issue "Repositories out of step"; `python3 scripts/sync-repos.py callers --repo NAME` opens the issue and the pull request that bring that repository in step. Run from a checkout that is `main` as it is now, the `org-sync` lane of [`policy/autonomy.yml`](../policy/autonomy.yml) accepts the issue, and the pull request merges on its own when every job it changes is its template's and none changes its permissions or secrets (a new job always waits); otherwise the maintainer accepts and merges them there. A new input a template asks to fill in goes into `repos.yml` (`callers`, `repository-owned`) in the same pull request, or the check would hold every repository to the template's example value.

Who signs what (#491) reaches the repositories in two steps. The release brings the rule (the `AGENTS.md` block, through `sync-repos.py files`), the conventions check at org.yml `attribution: warn` and the merge's trailers everywhere at once. Then each repository's part is a sub-issue of #491, accepted with it: remove any text of its own that contradicts the rule, give a public repository's `CONTRIBUTING.md` a "Credits" paragraph that points to [CONTRIBUTING.md, "Who signs what"](../CONTRIBUTING.md#who-signs-what), and in DiluxOne/dilux-agentic-workflow make `scripts/check_commits.py` and `ddw/rules/commits.instructions.md` accept `Assisted-by:` beside `AI-assisted:` and `AI-full:` and refuse a `Co-authored-by` only when it names a model, never a person: the cases `scripts/credits.py --test` marks C8 are the reference its tests mirror. Once every repository is in step, set `attribution: required`. On your own machine, `"includeCoAuthoredBy": false` in Claude Code's settings stops the trailer it adds by itself.

## The organisation's VM

The private repositories' jobs run on `vm-gh-runner-01` (Azure, `Standard_D8as_v5`: 8 cores, 32 GB, shared with AI Studio's own runners). Three slots per two cores (`dx-runner@1..12`, since a job waits on the disk more than on a core; `DX_SLOTS` overrides, #138, #379), each an endless loop of one-job containers of `ghcr.io/diluxone/runner:stable`, registered just in time through the `dilux-runner` App ([`scripts/runner-vm/dx-runner-slot.sh`](../scripts/runner-vm/dx-runner-slot.sh)). [`runner-vm.yml`](../.github/workflows/runner-vm.yml) starts the VM when a job waits and, after 20 minutes without one, cleans and deallocates it.

- **The data disk:** `vm-gh-runner-01-data128` on `/data` (every job's checkout, Docker's images and wp-env's databases): Premium SSD LRS, 256 GB, performance tier P15: 1100 IOPS baseline, 125 MB/s, credit bursting to 3500 IOPS, about USD 48 a month in chilecentral. It was Standard SSD E10 (500 IOPS), at 100% of its IOPS in 8 of 13 active hours over three days while CPU stayed at 20 to 28%; P15 rather than P20 because an idle backup P15 was already being paid for (now deleted) and CI's bursts fit the credit bursting. If it saturates again, the next step is the P20 tier on the same disk (`az disk update -n vm-gh-runner-01-data128 -g dilux-hosting-cl-rg --set tier=P20`, no data moved) ([#379](https://github.com/DiluxOne/.github/issues/379)).
- **What starts it.** A private repository's pull request: the organisation's pipeline calls [`runner-wake.yml`](../.github/workflows/runner-wake.yml), which dispatches `runner-vm.yml` with `start` on GitHub's runner: a few seconds, billed as one of the plan's minutes per push (GitHub rounds each job up), none on an edit of the description. Everything else (a push to `main`, an issue's triage, a repository's schedule, a re-run) waits for the clock: an Azure Function, `diluxone-runner-cl-prod-func` on the `dilux-cl-prod-linux-plan` App Service plan, dispatches `runner-vm.yml` with `auto` every five minutes as dilux-bot ([`scripts/runner-vm/clock/`](../scripts/runner-vm/clock/clock.py)), which also deallocates the VM once idle. It lives outside GitHub because GitHub ran `runner-vm.yml`'s ten-minute schedule only 4 to 6 times a day from 10 to 15 October, and jobs waited hours (#183); that schedule stays as the fallback. The Function's code deploys with `scripts/runner-vm/clock/deploy.sh`, run by whoever merges a change to that directory (nothing deploys on merge); if the Function stops, `runner-vm.yml` shows only scheduled runs again and #183's issue reopens as jobs wait; its settings (dilux-bot's client ID, installation ID and key, base64) are set once by an administrator, and its storage account (`diluxonerunnerclprodstr`) takes only its managed identity.
- **When a job waits too long:** every run of `runner-vm.yml` keeps one issue here, "Jobs waiting for the organisation's VM", listing each job queued for more than 15 minutes for a `diluxone` runner with its link, and closes it once none waits that long. If it is open, the VM is off or full: start it by hand (Actions, *Organisation VM*, `start`).
- **Changing the VM** is a pull request here: on every boot `dx-provision.service` fetches [`scripts/runner-vm/provision.sh`](../scripts/runner-vm/provision.sh) from `main` and runs it. Nobody changes the VM by hand.
- **Changing the image** is a pull request to [`runner/`](../runner/); [`runner-image.yml`](../.github/workflows/runner-image.yml) builds it on merge and every day, and promotes it to `:stable` only after its smoke test. Each build is an issue of its own, labelled `run:runner-image`: a promoted one closes as completed, a failed one stays open with `needs-human`. Dependabot moves only the digest of the Ubuntu release the image is on (the `ignore` this repository's `dependabot` entry in [`repos.yml`](../repos.yml) adds to its template); moving to a new release (24.04 to 26.04) is done by hand, once what setup-php installs from publishes for it: the ondrej/php PPA (PHP 7.4 to 8.2) and php-builder's prebuilt builds (8.3 and up). The smoke test sets PHP up from both and fails until then, and the Dockerfile's list of the libraries those builds link against may need the new release's package names.
- **Going back to an earlier image:** every promoted build also carries its date and run (`:YYYY-MM-DD.<run>`). Point `:stable` at one (`docker buildx imagetools create -t ghcr.io/diluxone/runner:stable ghcr.io/diluxone/runner:<that tag>`) and the slots take it on their next container.
- **Sending every job back to GitHub's runners:** set the organisation variable `DX_RUNNER_HEAVY` to `"ubuntu-latest"` (with the quotes: it is JSON). Nothing else changes; set it back to `["self-hosted","linux","x64","diluxone"]` to return.
- **A new VM:** Docker, the data disk on `/data` (Premium SSD, as above), the App's key and IDs in `/etc/dx-runner/app.pem` and `app.env` (root only; copies in the maintainer's secrets manager), then `provision.sh --install`.
- **The App's key** can only register runners. A job reaches the VM's Docker socket (wp-env needs it), which is root on the VM, so it could read the key; that is accepted because only the private repositories reach the VM (the runner group `private-repos-vm` admits them alone, and only they see `DX_RUNNER_HEAVY`), and a private repository has no outside forks: its pull requests come from the maintainer, the maintainer's agents and Dependabot. The pull requests dilux-bot opens from a reproduction carry a test written from an issue's text, so their checks never run on the VM ([`scripts/runner-route.py`](../scripts/runner-route.py), #167).
