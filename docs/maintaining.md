# Maintaining this repository

For whoever changes `DiluxOne/.github`: what the tokens may do, and how a change ships to every repository.

Every place the bot's token is minted asks only for what that job does: the review, the replies and the triage get `contents: read` while the model runs; `contents: write` is minted only by the merge, the reproduction push, the weekly learnings, and the step that resolves review threads after the model has finished (resolving a thread is a write on the repository), which nothing that read the pull request's text ever holds. Tags are not creatable by `dilux-bot` at all: the ruleset an adopting repository sets at step 3 allows `X.Y.Z` tag creation to administrators and the release App only, and this repository's `v*` tags (the moving `v5`, the frozen `v4`, `v3`, `v2` and `v1`) can be created, moved or deleted only by administrators (ruleset `moving tags`: creation, update, deletion). The wordpress.org credentials live in the repository environment `wordpress-org`, whose deployment policy admits only `X.Y.Z` tags and `main`, so no pull request or branch job can read them; the check `svn-auth-check.yml` runs inside that environment.

Almost everything here is high risk, and a human merges it. A change that touches only the pages people read (`README.md`, the Markdown of `profile/`, and `docs/` except what agents and the review read as rules: `docs/agents.md`, `docs/architecture.md`, `docs/testing-and-quality.md`) can merge on its own under the usual conditions; [`.github/review-policy.yml`](../.github/review-policy.yml) lists the rest, and `policy.py --test` fails when a file is in no list. After merging, move
`v5` (or cut `v6` for a breaking change: `scripts/next-version.py --tag-prefix v`
says which) and tag the exact version. Moving `v5` also ships the review
profiles, the packs, the default policy and the organisation's required
workflow, which every repository on `v5` reads from that tag. A run that
already exists keeps the workflow it was created with: re-running a failed
job after `v5` moved re-runs the old workflow. Reopen the pull request, or
push to it, for a run on the new one. `v4`, `v3`, `v2` and `v1` stay where
they are.

A change to a template in [`workflow-templates/`](../workflow-templates/) reaches no repository by itself: each one has its own copy, its caller. The weekly drift check lists every caller that differs from its template, with the job and the template's path (it compares what the jobs do, never their comments, so a template's comment can change without putting any repository out of step), in the issue "Repositories out of step"; `python3 scripts/sync-repos.py callers --repo NAME` opens the issue and the pull request that bring that repository in step, and the maintainer accepts and merges them there. A new input a template asks to fill in goes into `repos.yml` (`callers`, `repository-owned`) in the same pull request, or the check would hold every repository to the template's example value.

## The organisation's VM

The private repositories' jobs run on `vm-gh-runner-01` (Azure, `Standard_D8as_v5`: 8 cores, 32 GB, shared with AI Studio's own runners): one slot per core (`dx-runner@1..8`; `DX_SLOTS` overrides, #138), each an endless loop of one-job containers of `ghcr.io/diluxone/runner:stable`, registered just in time through the `dilux-runner` App ([`scripts/runner-vm/dx-runner-slot.sh`](../scripts/runner-vm/dx-runner-slot.sh)). [`runner-vm.yml`](../.github/workflows/runner-vm.yml) starts the VM when a job waits and, after 20 minutes without one, cleans and deallocates it.

- **What starts it.** A private repository's pull request: the organisation's pipeline calls [`runner-wake.yml`](../.github/workflows/runner-wake.yml), which dispatches `runner-vm.yml` with `start` on GitHub's runner: a few seconds, billed as one of the plan's minutes per push (GitHub rounds each job up), none on an edit of the description. Everything else (a push to `main`, an issue's triage, a repository's schedule) waits for `runner-vm.yml`'s schedule, every ten minutes, which GitHub delays or skips under load (none ran on 15 October from 00:07 to 01:01 UTC, #154). The schedule is the fallback, and still the only thing that deallocates the VM.
- **When a job waits too long:** every run of `runner-vm.yml` keeps one issue here, "Jobs waiting for the organisation's VM", listing each job queued for more than 15 minutes for a `diluxone` runner with its link, and closes it once none waits that long. If it is open, the VM is off or full: start it by hand (Actions, *Organisation VM*, `start`).
- **Changing the VM** is a pull request here: on every boot `dx-provision.service` fetches [`scripts/runner-vm/provision.sh`](../scripts/runner-vm/provision.sh) from `main` and runs it. Nobody changes the VM by hand.
- **Changing the image** is a pull request to [`runner/`](../runner/); [`runner-image.yml`](../.github/workflows/runner-image.yml) builds it on merge and every Monday, and promotes it to `:stable` only after its smoke test. Each promotion is a comment on the issue "Runner image". Dependabot moves only the digest of the Ubuntu release the image is on (the `ignore` this repository's `dependabot` entry in [`repos.yml`](../repos.yml) adds to its template); moving to a new release (24.04 to 26.04) is done by hand, once what setup-php installs from publishes for it: the ondrej/php PPA (PHP 7.4 to 8.2) and php-builder's prebuilt builds (8.3 and up). The smoke test sets PHP up from both and fails until then, and the Dockerfile's list of the libraries those builds link against may need the new release's package names.
- **Going back to an earlier image:** every promoted build also carries its date and run (`:YYYY-MM-DD.<run>`). Point `:stable` at one (`docker buildx imagetools create -t ghcr.io/diluxone/runner:stable ghcr.io/diluxone/runner:<that tag>`) and the slots take it on their next container.
- **Sending every job back to GitHub's runners:** set the organisation variable `DX_RUNNER` to `github`. Nothing else changes; set it back to `self-hosted` to return.
- **A new VM:** Docker, the data disk on `/data`, the App's key and IDs in `/etc/dx-runner/app.pem` and `app.env` (root only; copies in the maintainer's secrets manager), then `provision.sh --install`.
- **The App's key** can only register runners. A job reaches the VM's Docker socket (wp-env needs it), which is root on the VM, so it could read the key; that is accepted because only the private repositories reach the VM (the runner group `private-repos-vm` admits them alone, and only they see `DX_RUNNER`), and a private repository has no outside forks: its pull requests come from the maintainer, the maintainer's agents and Dependabot. The pull requests dilux-bot opens from a reproduction carry a test written from an issue's text, so their checks never run on the VM ([`scripts/runner-route.py`](../scripts/runner-route.py), #167).
